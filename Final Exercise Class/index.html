🚀 Challenge: Sakila Store Performance Dashboard

Build a small set of analytical queries that a store manager would actually want to see. Five steps. Each one uses something from a different block of the course.

The Scenario

You've been asked to put together a "store performance dashboard" on the Sakila database. The manager wants four numbers and one operational suggestion:

  1. Films per category, biggest categories first.
  2. Top 10 customers by total spend.
  3. Films that have no inventory (the "dead catalogue" list).
  4. A saved view for monthly revenue, so the manager can rerun it any time.
  5. An index suggestion that would help the dashboard's heaviest query.

Tables in play

film, film_category, category, inventory, payment, customer.

1Films per category

Join category with film_category and film. Count the films per category. Sort by count descending. (Hint: three tables, two INNER JOINs, one GROUP BY.)

2Top 10 customers by total spend

Join customer with payment. Per customer, return first_name, last_name, and total_spent (SUM(payment.amount), rounded to 2 decimals). Sort by total_spent descending, top 10.

3Films that have no inventory

Find films with no row in inventory. Use one LEFT JOIN, then keep rows where the inventory side is NULL.

4Save monthly revenue as a view (in testdb)

In your testdb, create a view monthly_revenue that returns year, month, payment count, and total revenue per (year, month). Once the view exists, the manager can run SELECT * FROM monthly_revenue ORDER BY y, m; any time.

5Suggest one index (advisory only)

Looking at the queries above, suggest one index that would speed at least one of them up. State the table, the column(s), and which query benefits. Write the CREATE INDEX statement as if you owned the database. (You don't have CREATE INDEX privilege on Sakila; this step is advisory, not for execution.)

Compare with the suggested solution

When you've worked through all five steps, click below to see one possible set of answers. Yours may differ in style; what matters is that each query is correct and uses the right tool for the job.

-- (1) Films per category
SELECT category.name AS category,
       COUNT(film.film_id) AS film_count
FROM       sakila.category
INNER JOIN sakila.film_category
          ON category.category_id = film_category.category_id
INNER JOIN sakila.film
          ON film_category.film_id = film.film_id
GROUP BY category.category_id, category.name
ORDER BY film_count DESC;

-- (2) Top 10 customers by total spend
SELECT customer.first_name, customer.last_name,
       ROUND(SUM(payment.amount), 2) AS total_spent
FROM       sakila.customer
INNER JOIN sakila.payment ON customer.customer_id = payment.customer_id
GROUP BY customer.customer_id, customer.first_name, customer.last_name
ORDER BY total_spent DESC
LIMIT 10;

-- (3) Films that have no inventory
SELECT film.title
FROM      sakila.film
LEFT JOIN sakila.inventory ON film.film_id = inventory.film_id
WHERE     inventory.inventory_id IS NULL;

-- (4) Monthly revenue view, saved in testdb
USE testdb;

CREATE VIEW monthly_revenue AS
SELECT YEAR(payment_date)         AS y,
       MONTH(payment_date)        AS m,
       COUNT(*)                   AS payments,
       ROUND(SUM(amount), 2)     AS revenue
FROM   sakila.payment
GROUP BY YEAR(payment_date), MONTH(payment_date);

-- The manager can now do this whenever they want a refresh:
-- SELECT * FROM monthly_revenue ORDER BY y, m;

-- (5) Suggested index (advisory)
-- Query 2 filters on payment.customer_id repeatedly (in the JOIN).
-- The customer_id column in payment is a perfect candidate for an index.
-- (In real Sakila there's already one; this is what you would write
--  if you owned the database. You can't run it in the lab.)
CREATE INDEX idx_payment_customer
  ON payment (customer_id);
What the dashboard tells the manager:
  • Which categories carry the catalogue (so they can stock more of the popular ones).
  • Who their top customers are by spend (for marketing).
  • Which films are out of circulation (the "dead catalogue" candidates).
  • Month-on-month revenue trend, ready to query any time.
  • One concrete operational tweak (the index) that keeps the dashboard responsive as data grows.
