Why we join

So far every query you wrote looked at one table at a time. Real reports almost always need information that's split across several tables, that's the whole reason databases use foreign keys.

The Sakila example we'll come back to

Last week, to find the store_id of stores that have the film BUCKET BROTHERHOOD in stock, you wrote a subquery:

SELECT DISTINCT store_id
FROM sakila.inventory
WHERE film_id = (
  SELECT film_id FROM sakila.film
  WHERE title = 'BUCKET BROTHERHOOD'
);

It works, but it reads as "go fetch this thing, now use it over here". A JOIN writes the same idea more directly: combine rows from inventory and film by their matching film_id, then filter on the title.

SELECT DISTINCT inventory.store_id
FROM   sakila.inventory
INNER JOIN sakila.film
       ON inventory.film_id = film.film_id
WHERE  film.title = 'BUCKET BROTHERHOOD';

Both return the same answer. The join version is often shorter, faster, and easier to read once you have a feel for it.

Mental model: a JOIN combines rows from two tables based on a matching rule. Pick a column in each that should be equal, and the database produces one row per matching pair.

Anatomy of a JOIN

The general shape of a two-table join:

SELECT <columns>
FROM   <table_a>
JOIN   <table_b>
  ON   <table_a>.<col> = <table_b>.<col>;

Each piece

  • FROM table_a, the first ("left") table.
  • JOIN table_b, the second ("right") table to combine with.
  • ON a.col = b.col, the matching rule: how to decide which row of A goes with which row of B.

Qualifying column names

When more than one table is in play, you write customer.first_name, not just first_name. Two tables might both have a name column, an unprefixed reference would be ambiguous and MySQL would refuse it. Following your PDF style, every example today fully qualifies its columns.

Optional aliases: once you're comfortable, you can write FROM customer c JOIN payment p ON c.customer_id = p.customer_id to shorten things. The full names work fine for learning.

INNER JOIN

An INNER JOIN (or just JOIN, the word "INNER" is optional) returns rows that have matching values in both tables. If a customer has no matching payment, or a payment has no matching customer, that row is dropped.

Example 1, customers with payments greater than $11

Find each customer's name alongside the payment amount, for payments greater than $11.

SELECT customer.first_name, customer.last_name, payment.amount
FROM   sakila.customer
INNER JOIN sakila.payment
       ON customer.customer_id = payment.customer_id
WHERE  payment.amount > 11;

Read it: take rows from customer, for each one find every payment row whose customer_id matches, drop everything where the amount isn't more than 11.

Example 2, finding stores that stock a specific film

Find the store_ids that have inventory of the film BUCKET BROTHERHOOD.

SELECT DISTINCT inventory.store_id
FROM   sakila.inventory
INNER JOIN sakila.film
       ON inventory.film_id = film.film_id
WHERE  film.title = 'BUCKET BROTHERHOOD';

Example 3, retrieving customer 1's address

Get the street address of customer_id 1.

SELECT address.address
FROM   sakila.address
INNER JOIN sakila.customer
       ON address.address_id = customer.address_id
WHERE  customer.customer_id = 1;

The same task you solved last week with a subquery, now as a join. Cleaner, and it generalises easily, swap the filter to grab any customer's address.

LEFT JOIN

The table on the left side of the join determines how many rows you get in the result. The right side just contributes column values where a match is found. If there's no match, the right-side columns come back as NULL.

Written LEFT JOIN or LEFT OUTER JOIN, the two forms mean the same thing.

Example, films with IDs 13 to 15 and their inventory

Retrieve the film IDs, titles, and inventory IDs for films with IDs between 13 and 15, including films that don't have associated inventory records.

SELECT film.film_id, film.title, inventory.inventory_id
FROM   sakila.film
LEFT JOIN sakila.inventory
       ON film.film_id = inventory.film_id
WHERE  film.film_id BETWEEN 13 AND 15;

What comes back

Film 14, ALICE FANTASIA, has no row in inventory. With an INNER JOIN it would have been dropped. With LEFT JOIN it appears once, with a NULL for inventory.inventory_id. Films 13 and 15, which do have inventory, appear once per inventory row.

The "find rows with no match" pattern

Find every film that has no inventory record at all.

SELECT film.film_id, film.title
FROM      sakila.film
LEFT JOIN sakila.inventory
       ON film.film_id = inventory.film_id
WHERE     inventory.inventory_id IS NULL;
Why this works: after a LEFT JOIN, unmatched left rows have NULLs on the right. Filtering WHERE right.col IS NULL keeps exactly those rows, the ones that had no match.

RIGHT JOIN

RIGHT JOIN is the mirror of LEFT JOIN. The table on the right side of the join determines how many rows you get, while the left side just provides column values where matches exist.

Same scenario, RIGHT JOIN version

Same films-and-inventory query, this time keeping every inventory row.

SELECT film.film_id, film.title, inventory.inventory_id
FROM   sakila.film
RIGHT JOIN sakila.inventory
       ON film.film_id = inventory.film_id
WHERE  film.film_id BETWEEN 13 AND 15;

Film 14 (ALICE FANTASIA) is gone from this result. It has no row in inventory, so there is nothing on the right side to keep. Only films 13 and 15 survive, with one row per inventory entry.

You'll rarely write one

Anything you can write with RIGHT JOIN you can also write with LEFT JOIN by swapping the table order. Most teams pick a convention (usually LEFT) and stick with it for readability.

So why teach it? Because you will read code that uses it. Knowing how to read RIGHT JOIN is enough; you can keep writing LEFT JOIN in your own queries.

ON vs USING

The matching rule is most often written with ON, but when the joining column has the same name in both tables, you can use the shorter USING.

Same join, two styles

-- (1) The general form, ON with a predicate
SELECT customer.first_name, address.address
FROM   sakila.customer
JOIN   sakila.address
       ON customer.address_id = address.address_id;

-- (2) USING, shorter when both columns share a name
SELECT customer.first_name, address.address
FROM   sakila.customer
JOIN   sakila.address USING (address_id);

ON (general)

  • Works for any condition, including different column names
  • Most explicit, most common in production code
  • Best default choice

USING

  • Shorter when column names match
  • Returns the shared column only once
  • Slightly less flexible if you ever need a more complex condition
Rule of thumb: use ON by default. Reach for USING when you like its brevity and the column names match exactly.

Joining three tables (or more)

Just chain the joins. Each new JOIN ... ON ... brings one more table into the running result.

Example, every film customer 1 has rented

Find the titles of every distinct film rented by customer_id 1.

SELECT DISTINCT film.title
FROM      sakila.film
INNER JOIN sakila.inventory
          ON film.film_id = inventory.film_id
INNER JOIN sakila.rental
          ON inventory.inventory_id = rental.inventory_id
WHERE     rental.customer_id = 1;

Read it like a path: film ➜ inventory ➜ rental. The first JOIN connects film to its inventory rows. The second connects inventory to its rental rows. The WHERE filters down to customer 1. The same task you wrote last week as a triply nested IN-subquery, now in one clean pass.

Another, customers with their city

Show each customer's name and city.

SELECT customer.first_name, customer.last_name, city.city
FROM      sakila.customer
INNER JOIN sakila.address
          ON customer.address_id = address.address_id
INNER JOIN sakila.city
          ON address.city_id = city.city_id
LIMIT 10;

⚡ Quick check

In the customer ➜ address ➜ city chain above, if you change the first JOIN to LEFT JOIN, what happens to a customer whose address_id doesn't match any row in address?

Putting it together, joins with aggregation

"Top 10 customers by total spend, with their name."

Joins really earn their keep when paired with GROUP BY. The recipe: join the tables you need columns from, group by the entity you're summarising, then aggregate.

Step 1, the join

SELECT customer.customer_id, customer.first_name,
       customer.last_name, payment.amount
FROM   sakila.customer
INNER JOIN sakila.payment
       ON customer.customer_id = payment.customer_id;

Step 2, group by customer and aggregate

SELECT customer.customer_id,
       customer.first_name,
       customer.last_name,
       COUNT(payment.payment_id)         AS num_payments,
       ROUND(SUM(payment.amount), 2) AS total_spent
FROM   sakila.customer
INNER JOIN sakila.payment
       ON customer.customer_id = payment.customer_id
GROUP BY customer.customer_id, customer.first_name, customer.last_name;

Step 3, sort and crop

SELECT customer.customer_id,
       customer.first_name,
       customer.last_name,
       COUNT(payment.payment_id)         AS num_payments,
       ROUND(SUM(payment.amount), 2) AS total_spent
FROM   sakila.customer
INNER JOIN sakila.payment
       ON customer.customer_id = payment.customer_id
GROUP BY customer.customer_id, customer.first_name, customer.last_name
ORDER BY total_spent DESC
LIMIT 10;
Compare to Lecture 7: back then you grouped on payment alone and got customer_ids. The join here brings in first_name and last_name from customer, so the report is readable in one query.

You Made It! 🎉

You can now combine columns from several tables in one query, which is the bread and butter of real-world SQL.

Recap, what we covered

  • Why join: data is split across tables for good reasons; queries usually need to put it back together.
  • INNER JOIN: only rows that match in both tables.
  • LEFT JOIN: every left row, NULLs on the right where there's no match. Use WHERE right.col IS NULL to find unmatched rows.
  • RIGHT JOIN: mirror of LEFT, rarely written.
  • ON vs USING: use ON by default; USING(col) is a shorthand when columns share a name.
  • Three-table joins: chain JOINs left to right, following foreign keys.
  • JOIN + GROUP BY: the standard recipe for reports that summarise data from one table while displaying names from another.
  • Subquery vs JOIN: many of last week's subquery examples become cleaner as joins.
