Aggregation, the big idea

Until now, every SELECT we wrote gave back one output row per input row that survived the WHERE. Aggregation flips that. It takes many input rows and squeezes them into one summary value.

From rows to a number

-- 16,049 rows in payment, just one number out:
SELECT COUNT(*) AS total_payments
FROM payment;

The result is a single row, single column: the count of rows in payment. The five aggregate functions you'll meet today all share that shape: they read many rows, return one summary.

The five core aggregates

  • COUNT(...), how many.
  • SUM(col), total of the column's values.
  • AVG(col), mean of the column's values.
  • MIN(col), smallest value.
  • MAX(col), largest value.
Mental model: aggregate functions are reducers. They take a column of values and reduce it to one. Everything else in this lecture is about controlling what set of rows that reduction happens over.

COUNT in three flavors

COUNT has three useful shapes. Pick the right one for the question you're answering.

-- (1) Count every row, including ones with NULL columns
SELECT COUNT(*) AS total_rows FROM rental;

-- (2) Count rows where return_date is not NULL
SELECT COUNT(return_date) AS returned_rentals FROM rental;

-- (3) Count how many distinct customers ever rented anything
SELECT COUNT(DISTINCT customer_id) AS renters FROM rental;

The NULL gotcha

COUNT(*) counts the row no matter what. COUNT(column) skips rows where that column is NULL. That difference is what tells you, for instance, how many rentals have actually been returned.

Rule of thumb: use COUNT(*) when you want "how many rows", COUNT(col) when you want "how many non-NULL values", and COUNT(DISTINCT col) when you want "how many unique values".

⚡ Quick check

The customer table has 599 rows, and 14 of them have a NULL email. What does SELECT COUNT(email) FROM customer; return?

SUM, AVG, MIN, MAX

These four share the same shape. They take a column, they ignore NULLs, they give you one number back.

-- Total revenue ever collected by the Sakila store
SELECT SUM(amount) AS total_revenue FROM payment;

-- Average rental price across the catalogue
SELECT AVG(rental_rate) AS avg_price FROM film;

-- Shortest and longest films, side by side
SELECT MIN(length) AS shortest_minutes,
       MAX(length) AS longest_minutes
FROM film;

You can mix them in one SELECT

SELECT COUNT(*)       AS films,
       MIN(length)    AS shortest,
       MAX(length)    AS longest,
       AVG(length)    AS avg_length,
       SUM(length)    AS total_minutes
FROM film;

This is a one-line catalogue summary. Five aggregates on the same column, one row of output.

Rounding tip: AVG often comes back with many decimal places. Wrap it in ROUND(AVG(rental_rate), 2) if you want a tidy display.

GROUP BY, splitting rows into buckets

So far, aggregates summarised the whole table. Often you want one summary per category: per rating, per store, per month. GROUP BY is the tool.

The shape of a grouped query

SELECT rating, COUNT(*) AS film_count
FROM film
GROUP BY rating;

Read it as: "split the film rows into groups by rating, then count each group". One row out per distinct rating.

What the result looks like

ratingfilm_count
G178
PG194
PG-13223
R195
NC-17210
Visual: imagine the database stacking the 1,000 film rows into 5 piles by rating, then running COUNT(*) on each pile. You get back one row per pile.

The GROUP BY rule

There is one rule that catches every beginner once. It's worth saying clearly:

Rule: every column in the SELECT list must either be an aggregate or appear in the GROUP BY clause. Anything else is ambiguous.

Why?

Think about it. If you group films by rating and then ask for title, which title should the database show? There are 178 G-rated films, the database can't pick one. So it refuses.

-- WRONG: title is neither aggregated nor in GROUP BY
SELECT rating, title, COUNT(*)
FROM film
GROUP BY rating;
-- Error in MySQL strict mode (sql_mode=only_full_group_by)

-- RIGHT: length aggregated, so the database can pick one value per group
SELECT rating, MIN(length) AS shortest_minutes, COUNT(*)
FROM film
GROUP BY rating;
Reading habit: when you see a GROUP BY, scan the SELECT list and check each column. Is it inside an aggregate? Is it in the GROUP BY? If neither, something is wrong.

GROUP BY with multiple columns

List several columns after GROUP BY, separated by commas. The database groups by every unique combination of those columns.

-- Films per rating, broken down further by rental_duration
SELECT rating,
       rental_duration,
       COUNT(*)              AS film_count,
       ROUND(AVG(rental_rate), 2) AS avg_price
FROM film
GROUP BY rating, rental_duration
ORDER BY rating, rental_duration;

A peek at the result

If rating has 5 distinct values and rental_duration has 5 distinct values, what is the maximum number of rows that GROUP BY rating, rental_duration can produce?

HAVING, filtering the groups

Once the rows are split into groups, you sometimes want to keep only some of those groups. WHERE can't help here, because aggregates aren't even computed yet when WHERE runs. That's what HAVING is for.

Basic shape

-- Only ratings that have more than 200 films
SELECT rating, COUNT(*) AS film_count
FROM film
GROUP BY rating
HAVING COUNT(*) > 200;

You can reference an alias from SELECT

SELECT rating, COUNT(*) AS film_count
FROM film
GROUP BY rating
HAVING film_count > 200
ORDER BY film_count DESC;

HAVING can also mix aggregate and group columns

-- Ratings where the average price exceeds $3.00
SELECT rating, ROUND(AVG(rental_rate), 2) AS avg_price
FROM film
GROUP BY rating
HAVING AVG(rental_rate) > 3.00;
Rule of thumb: if the condition involves an aggregate (COUNT, SUM, AVG, MIN, MAX), it has to go in HAVING. If it's about a plain column value, it should go in WHERE.

WHERE vs HAVING, the execution order

Both filter rows out of the result, but they run at different stages of the pipeline. Understanding the order saves you from many confusing errors.

Logical execution order of a SELECT

  1. FROM, pick the table(s).
  2. WHERE, throw away rows that fail the row-level filter.
  3. GROUP BY, bundle the survivors into groups.
  4. HAVING, throw away whole groups that fail the group-level filter.
  5. SELECT, compute the columns (including aggregates).
  6. ORDER BY, sort the result.
  7. LIMIT, crop to the top N.

Same query, different filter stages

-- WHERE filters individual films before grouping (cheaper)
SELECT rating, COUNT(*) AS film_count
FROM film
WHERE length > 120             -- only long films
GROUP BY rating
HAVING COUNT(*) >= 50;       -- only ratings with 50+ long films

WHERE

  • Runs before GROUP BY
  • Filters individual rows
  • Can't use aggregates
  • Can't use SELECT aliases

HAVING

  • Runs after GROUP BY
  • Filters whole groups
  • Aggregates are allowed here
  • Can use SELECT aliases (in MySQL)
Common mistake: writing WHERE COUNT(*) > 200. That's illegal, because COUNT(*) doesn't exist yet when WHERE runs. Move it to HAVING.

Aggregates and NULL

The aggregate functions all share one quirk worth memorising: they ignore NULLs, except for COUNT(*).

What that means in practice

  • COUNT(*) counts every row, regardless of NULLs.
  • COUNT(col) counts rows where col is not NULL.
  • SUM, AVG, MIN, MAX all skip NULL values before computing.
  • AVG divides by the number of non-NULL values, not the total row count.

A small example

-- Imagine a 4-row table where score has one NULL
--   score: 4, 6, NULL, 8

SELECT COUNT(*)     -- 4 (all rows)
     , COUNT(score) -- 3 (NULL skipped)
     , SUM(score)   -- 18 (4 + 6 + 8)
     , AVG(score)   -- 6.0 (18 / 3, not 18 / 4)
     , MIN(score)   -- 4
     , MAX(score);  -- 8
Subtle bug: if you want to "treat NULL as zero" in an average, the aggregate won't do that on its own. Wrap the column: AVG(IFNULL(score, 0)). Then the NULL becomes a 0 and joins the denominator.

What if every value is NULL?

SUM, AVG, MIN, MAX all return NULL. Only COUNT returns 0, because counting an empty set is still a meaningful answer.

GROUP BY with expressions

You don't have to group by a raw column. Any expression works: a function call, an arithmetic expression, or a CASE.

Group payments by year

SELECT YEAR(payment_date) AS pay_year,
       COUNT(*)             AS payments,
       ROUND(SUM(amount), 2) AS revenue
FROM payment
GROUP BY YEAR(payment_date)
ORDER BY pay_year;

Group by year and month together

SELECT YEAR(payment_date)  AS y,
       MONTH(payment_date) AS m,
       COUNT(*)             AS payments,
       ROUND(SUM(amount), 2) AS revenue
FROM payment
GROUP BY YEAR(payment_date), MONTH(payment_date)
ORDER BY y, m;
Why this is useful: raw date columns are too fine-grained to summarise. Pulling out the year (or year + month) with YEAR and MONTH gives the database a coarser bucket to group by, and the report becomes readable.

Putting it together, a worked report

"Who are our top 10 customers by total spend in 2005, ignoring tiny transactions?"

Step 1, plain SELECT

SELECT customer_id, amount, payment_date
FROM payment;

Step 2, filter rows with WHERE

SELECT customer_id, amount, payment_date
FROM payment
WHERE YEAR(payment_date) = 2005
  AND amount >= 2.00;

Step 3, aggregate by customer

SELECT customer_id,
       COUNT(*)            AS num_payments,
       ROUND(SUM(amount), 2) AS total_spent
FROM payment
WHERE YEAR(payment_date) = 2005
  AND amount >= 2.00
GROUP BY customer_id;

Step 4, keep only the big spenders with HAVING

SELECT customer_id,
       COUNT(*)            AS num_payments,
       ROUND(SUM(amount), 2) AS total_spent
FROM payment
WHERE YEAR(payment_date) = 2005
  AND amount >= 2.00
GROUP BY customer_id
HAVING SUM(amount) > 100;

Step 5, sort and crop

SELECT customer_id,
       COUNT(*)            AS num_payments,
       ROUND(SUM(amount), 2) AS total_spent
FROM payment
WHERE YEAR(payment_date) = 2005
  AND amount >= 2.00
GROUP BY customer_id
HAVING SUM(amount) > 100
ORDER BY total_spent DESC
LIMIT 10;
Notice the layering: WHERE narrows rows, GROUP BY bundles them, HAVING narrows groups, ORDER BY sorts what's left, LIMIT crops. Every clause has a different job; together they answer a complete business question.

You Made It! 🎉

You can now answer "how many", "total", "average", and "biggest/smallest" questions, both for whole tables and for slices of them.

Recap, what we covered

  • Aggregates: COUNT, SUM, AVG, MIN, MAX, all reduce many rows to one summary.
  • COUNT(*) vs COUNT(col) vs COUNT(DISTINCT col), three different questions, three different shapes.
  • GROUP BY, split the rows into buckets so each aggregate is computed per bucket.
  • The GROUP BY rule: every non-aggregate column in SELECT must appear in GROUP BY.
  • HAVING, the filter for whole groups (aggregates allowed here, not in WHERE).
  • Execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
  • Aggregates and NULL: all aggregates except COUNT(*) skip NULLs. AVG divides by non-NULL count only.
  • GROUP BY expressions: group by YEAR(date), FLOOR(...), or any expression, not just raw columns.
