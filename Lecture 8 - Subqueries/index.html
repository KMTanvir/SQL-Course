What is a subquery?

A subquery is a SELECT statement written inside another SQL statement, always wrapped in parentheses. The inner query runs first (conceptually), produces a result, and the outer query uses that result as a value.

A first taste

-- Films priced above the catalogue average
SELECT title, rental_rate
FROM film
WHERE rental_rate > (
  SELECT AVG(rental_rate) FROM film
);

The inner query computes one number, the catalogue average. The outer query then compares every film against that number. Two queries, one statement.

Three shapes by what the inner query returns

  • Scalar: one row, one column. Behaves like a single value.
  • Row: one row, several columns.
  • Table: many rows. Used with IN or EXISTS.
Mental model: a subquery is just another query whose result becomes an input. Treat the inner query as a black box that returns "something", and ask: is the outer query expecting a single value, a list, or a yes/no answer?

Scalar subqueries

A scalar subquery returns exactly one row and one column. That makes it behave like a literal value, you can use it anywhere a single value goes.

Anatomy

-- The inner query returns exactly one number:
SELECT AVG(rental_rate) FROM film;
-- Result: 2.98

-- That number is then used as if you had typed 2.98:
SELECT title, rental_rate
FROM film
WHERE rental_rate > (SELECT AVG(rental_rate) FROM film);

Why use a scalar subquery instead of typing the number?

Because the average changes as the data changes. The subquery recomputes the value every time the outer query runs, so your filter stays correct without manual updates.

Common pitfall: if the inner query returns more than one row, MySQL raises Subquery returns more than 1 row. Aggregates (AVG, MAX, MIN, SUM, COUNT) always return one row, so they are safe scalar subqueries.

Subqueries with comparison operators

When the inner query is scalar, you can use any comparison operator: =, <>, <, >, <=, >=.

The most expensive film(s)

SELECT title, rental_rate
FROM film
WHERE rental_rate = (
  SELECT MAX(rental_rate) FROM film
);

The inner query finds the maximum price. The outer query returns every film priced at that exact value. (There can be ties, so you may get more than one row.)

Films shorter than the average length

SELECT title, length
FROM film
WHERE length < (
  SELECT AVG(length) FROM film
)
ORDER BY length;

Films released no earlier than customer 1's join year

SELECT title, release_year
FROM film
WHERE release_year >= (
  SELECT YEAR(create_date) FROM customer WHERE customer_id = 1
);

Here the inner query returns one value (the create-year of customer 1), and the outer query uses it as a threshold.

Habit to build: when you write a scalar subquery inside a comparison, mentally ask "does this always return one row?". Aggregates do. WHERE id = some_unique_value does. WHERE rating = 'PG' usually doesn't.

IN with a subquery

When the inner query returns multiple values, you use IN instead of =. It's the same IN you used last week with a hardcoded list, except now the list comes from a query.

Customers who belong to store 1

-- Hardcoded list version:
SELECT first_name, last_name
FROM customer
WHERE customer_id IN (1, 2, 3, 4, 5);

-- Subquery version, the list comes from another query:
SELECT first_name, last_name
FROM customer
WHERE customer_id IN (
  SELECT customer_id FROM customer WHERE store_id = 1
);

Films that have at least one actor named PENELOPE

SELECT title
FROM film
WHERE film_id IN (
  SELECT film_id
  FROM film_actor
  WHERE actor_id IN (
    SELECT actor_id FROM actor WHERE first_name = 'PENELOPE'
  )
);

Nested subqueries are fine. Each level peels off one step toward the answer: from actor name to actor ID, from actor ID to film ID, from film ID to title.

Rule of thumb: when the inner query produces a column of values, use IN. When it produces a single number or string, use = (or any other comparison operator).

EXISTS and NOT EXISTS

EXISTS takes a subquery and returns true if that subquery produces at least one row, false otherwise. NOT EXISTS is its inverse.

Customers who have ever rented at least once

SELECT customer_id, first_name, last_name
FROM customer c
WHERE EXISTS (
  SELECT 1 FROM rental r WHERE r.customer_id = c.customer_id
);

For each customer row, the inner query asks "is there at least one rental linked to this customer?". If yes, the row survives.

Customers who have never rented anything

SELECT customer_id, first_name, last_name
FROM customer c
WHERE NOT EXISTS (
  SELECT 1 FROM rental r WHERE r.customer_id = c.customer_id
);

Why SELECT 1?

Inside EXISTS the column list does not matter, only whether any row comes back. Writing SELECT 1 is a convention that says "I don't care what columns, just check existence". SELECT * works too; both are equivalent here.

Putting it together, a worked example

"List the customers who have ever rented one of the most expensive films."

Step 1, find the maximum rental rate

SELECT MAX(rental_rate) FROM film;
-- Result: 4.99

Step 2, find the film_ids priced at that maximum

SELECT film_id
FROM film
WHERE rental_rate = (SELECT MAX(rental_rate) FROM film);

Step 3, find the inventory rows for those films

SELECT inventory_id
FROM inventory
WHERE film_id IN (
  SELECT film_id FROM film
  WHERE rental_rate = (SELECT MAX(rental_rate) FROM film)
);

Step 4, find customers whose rentals match those inventory rows

SELECT DISTINCT customer_id
FROM rental
WHERE inventory_id IN (
  SELECT inventory_id FROM inventory
  WHERE film_id IN (
    SELECT film_id FROM film
    WHERE rental_rate = (SELECT MAX(rental_rate) FROM film)
  )
);
What just happened: we layered three subqueries, each peeling off one step toward the answer. The innermost finds the max rate (scalar). The middle two filter by IN using the result of the level below. DISTINCT at the top deduplicates customers who rented more than one expensive film.
Next time: the same answer with a join is shorter and usually faster. Subqueries shine when you want a value to compare against; joins shine when you want columns from another table.

You Made It! 🎉

Subqueries let one query feed another. You can compute thresholds, build lists, and check existence, all without leaving SQL.

Recap, what we covered

  • Subquery: a SELECT in parentheses, used inside another SQL statement.
  • Scalar subquery: one row, one column. Behaves like a single value, works with =, <, >, and the rest.
  • IN with subquery: the list of values comes from a query, not a hardcoded list.
  • EXISTS / NOT EXISTS: boolean check on whether the subquery produces any rows. Use SELECT 1 inside by convention.
  • Pitfalls: a scalar comparison fails if the inner query returns more than one row. Always know what shape your inner query has.
