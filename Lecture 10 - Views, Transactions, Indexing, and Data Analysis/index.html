Views, what and why

A view is a virtual table based on a saved SQL query. It does not store data on its own; every time you query the view, the database runs the saved query underneath and returns the result.

Why bother?

  • Reuse: if a join or aggregate keeps showing up, save it once and use it many times.
  • Simplicity: hide the joins and complexity behind a clean name. Analysts can write SELECT * FROM customer_payment instead of remembering a four-table chain.
  • Consistency: everyone in the team queries the same definition of "total spend per customer".

What a view is not

  • Not a copy of the data. It re-runs the underlying query each time.
  • Not necessarily faster. The work still happens; you just don't have to type it.
  • Not always updateable. Simple views can take INSERT/UPDATE; views that aggregate or join usually cannot.
Mental model: a view is a query with a name. The name behaves like a table when you read from it, the saved query runs in the background.

Creating and querying a view

Create

USE testdb;

CREATE VIEW earn AS
SELECT payment_id, payment_date, amount
FROM   sakila.payment;

The view is created in your own testdb, but its SELECT pulls from sakila.payment. That's the standard pattern in the lab: read from Sakila, save your analytical views in testdb where you have write privileges.

Query, just like a table

SELECT * FROM earn;

-- Apply any normal SQL on top of it
SELECT YEAR(payment_date) AS y, SUM(amount) AS total
FROM   earn
GROUP BY YEAR(payment_date);
Lab note: in your ISRT account you can CREATE VIEW in testdb, but you don't have privileges to DROP or REPLACE objects. So pick a fresh name when you create a new view; you can't overwrite an existing one. CREATE OR REPLACE VIEW and DROP VIEW exist in MySQL; you'll see them in tutorials and in production work, but they aren't part of this lab.
Naming habit: give views descriptive names with a consistent prefix or suffix (e.g., v_customer_payment). Helps anyone reading a query tell views apart from base tables.

Views on aggregated data

Where views earn their keep is on aggregates and multi-table joins. Save the complex query once, then keep your analysis simple.

A view for per-customer total payment

CREATE VIEW customer_payment AS
SELECT customer_id, SUM(amount) AS total_payment
FROM   sakila.payment
GROUP BY customer_id;

Now any analysis on top is a one-liner

-- Customers who have spent more than $100
SELECT customer_id, total_payment
FROM   customer_payment
WHERE  total_payment > 100;

-- Top 10 spenders
SELECT customer_id, total_payment
FROM   customer_payment
ORDER BY total_payment DESC
LIMIT 10;

The view stays current

The view doesn't store the aggregated numbers. Every time you query it, MySQL recomputes SUM(amount) ... GROUP BY customer_id against the latest data. If a new payment lands tomorrow, the view shows the new totals immediately.

Transactions, the idea

A transaction is a group of one or more SQL statements that are treated as one unit of work. Either every statement succeeds and the changes become permanent, or none of them stick.

The motivating example

A bank transfer: deduct $300 from Alice's account, add $300 to Bob's. If the first UPDATE succeeds but the second one fails (network drops, server crashes, anything), Alice has lost $300 that never reached Bob. A transaction prevents this.

The four commands you'll use

CommandDescription
START TRANSACTIONBegin a transaction. Every statement after this is part of one unit.
COMMITSave all changes made by the transaction permanently.
ROLLBACKUndo every change made since the START TRANSACTION.
SAVEPOINT nameMark a point inside the transaction you can roll back to without losing earlier work.
RELEASE SAVEPOINT nameForget the savepoint (no further rollback to it possible).
Setup we'll use: a small bank_accounts008 table with Alice (1000), Bob (1500), Charlie (2000), David (2500). Practice transactions on this, not Sakila, because we'll be modifying balances.

START, COMMIT, ROLLBACK

Setup

USE testdb;

CREATE TABLE bank_accounts008 (
  account_id   INT PRIMARY KEY,
  account_name VARCHAR(50),
  balance      DECIMAL(10, 2)
);

INSERT INTO bank_accounts008 VALUES
  (101, 'Alice',   1000),
  (102, 'Bob',     1500),
  (103, 'Charlie', 2000),
  (104, 'David',   2500);

Alice transfers $300 to Bob (COMMIT)

START TRANSACTION;

UPDATE bank_accounts008
SET balance = balance - 300
WHERE account_id = 101;

UPDATE bank_accounts008
SET balance = balance + 300
WHERE account_id = 102;

COMMIT;

Both UPDATEs run, then COMMIT makes them permanent together. Other users only see the new balances after the COMMIT.

Charlie tries to overdraw (ROLLBACK)

START TRANSACTION;

UPDATE bank_accounts008
SET balance = balance - 5000
WHERE account_id = 103;

-- Check; Charlie now shows -3000, which is invalid
SELECT account_id, balance FROM bank_accounts008;

-- Undo everything since START TRANSACTION
ROLLBACK;

After ROLLBACK, Charlie's balance is back to 2000. None of the changes since START TRANSACTION survive.

SAVEPOINT and RELEASE SAVEPOINT

A savepoint is a checkpoint inside a transaction. You can roll back to it without losing the earlier work in the same transaction.

David withdraws $100, but we cancel adding money to Alice

START TRANSACTION;

-- Deduct $100 from David
UPDATE bank_accounts008
SET balance = balance - 100
WHERE account_id = 104;

SAVEPOINT before_second_update;

-- Add $100 to Alice
UPDATE bank_accounts008
SET balance = balance + 100
WHERE account_id = 101;

-- Cancel only the second UPDATE
ROLLBACK TO before_second_update;

COMMIT;

End state: David's $100 deduction is committed; Alice's addition was rolled back. The savepoint let us keep part of the transaction and discard the rest.

Releasing a savepoint

-- Once we decide we won't need the savepoint anymore, release it
RELEASE SAVEPOINT before_second_update;
COMMIT;
When to use savepoints: long transactions where some operations are riskier than others (e.g., bulk inserts where you want to bail out of a subset without throwing away the parts that worked). Most everyday transactions don't need them.

Concurrency: isolation levels and deadlocks

When several users hit the database at the same time, transactions can interfere with each other. SQL has two safety nets, isolation levels and locks, plus one famous failure mode, the deadlock.

Isolation levels

An isolation level controls how much one transaction is allowed to see the in-progress changes of another. Higher isolation means safer behaviour, but more locking and slower throughput. MySQL's default is REPEATABLE READ; you can change it with SET TRANSACTION ISOLATION LEVEL ... when needed.

What a deadlock is

Two transactions each hold a lock the other one needs. Neither can move forward. The database eventually picks one as the "victim" and aborts it; the other one proceeds.

-- Transaction 1                            -- Transaction 2
START TRANSACTION;                         START TRANSACTION;
UPDATE accounts                            UPDATE accounts
SET balance = balance - 100                SET balance = balance + 100
WHERE account_id = 1;                      WHERE account_id = 2;
-- T1 has locked account 1                  -- T2 has locked account 2

UPDATE accounts                            UPDATE accounts
SET balance = balance + 100                SET balance = balance - 100
WHERE account_id = 2;                      WHERE account_id = 1;
-- T1 waits for account 2                   -- T2 waits for account 1
-- (T2 has it)                              -- (T1 has it)

-- DEADLOCK. MySQL kills one transaction with an error.
How to avoid them: always update tables in the same order across transactions, keep transactions short, and don't hold them open during long client-side work. We won't go deeper here; this is enough to recognise the pattern.

Indexing, the idea

An index is a data structure that speeds up data retrieval. It works like the index at the back of a book: instead of flipping through every page (a "full table scan"), the database looks up your search term in the index and jumps straight to the matching rows.

The shape of the win

Find accounts with balance greater than 1500.

  • Without an index: SQL scans every row, comparing each balance to 1500. Slow on big tables.
  • With an index on balance: SQL jumps to the first row at 1500 in the sorted index and reads forward.

Things to know

  • A PRIMARY KEY automatically gets an index. So does a column declared UNIQUE.
  • Indexes store a pointer to the actual row, not a copy of the row.
  • Indexes speed up SELECT but slow down INSERT, UPDATE, and DELETE a little, because the index has to be updated too.
  • Indexes use disk space.
Trade-off: don't index every column. Add an index when you have a slow query that filters or joins on that column repeatedly. Otherwise you're paying the cost without getting much back.

CREATE INDEX and composite indexes

A single-column index

CREATE INDEX idx_account_name
  ON bank_accounts008 (account_name);

Helps queries like:

SELECT * FROM bank_accounts008
WHERE account_name = 'Alice';

A composite (multi-column) index

When your query filters on two columns together, a composite index can help. The order of columns in the index matters; the leftmost column is the primary one.

CREATE INDEX idx_name_balance
  ON bank_accounts008 (account_name, balance);

Helps queries like:

SELECT * FROM bank_accounts008
WHERE account_name = 'Charlie' AND balance > 1500;
Lab note: MySQL also has DROP INDEX idx_name ON table; to remove an index. In your lab account you don't have privileges to drop, so once you create an index here it stays. Choose names you can live with.

Data analysis with SQL, putting it together

A small worked analysis: who are Sakila's high-value customers? Save the heavy work once as a view, then ask different questions of it.

Step 1, save the building block as a view

USE testdb;

CREATE VIEW customer_spend AS
SELECT customer.customer_id,
       customer.first_name,
       customer.last_name,
       COUNT(payment.payment_id)         AS num_payments,
       ROUND(SUM(payment.amount), 2) AS total_spent
FROM       sakila.customer
INNER JOIN sakila.payment
          ON customer.customer_id = payment.customer_id
GROUP BY customer.customer_id, customer.first_name, customer.last_name;

Step 2, top 10 spenders, straight from the view

SELECT * FROM customer_spend
ORDER BY total_spent DESC
LIMIT 10;

Step 3, customers spending more than $150

SELECT customer_id, first_name, last_name, total_spent
FROM   customer_spend
WHERE  total_spent > 150
ORDER BY total_spent DESC;

Step 4, customers who made more than 30 payments

SELECT customer_id, first_name, last_name, num_payments, total_spent
FROM   customer_spend
WHERE  num_payments > 30
ORDER BY num_payments DESC;
What this shows: the view turns a complex pre-computation (the JOIN + GROUP BY) into a clean, reusable name. After that, every new question against the same data is a short query: just a WHERE and an ORDER BY on the view. That's the everyday rhythm of SQL-based data analysis.

Recap of today

  • Views: a saved SELECT with a name. Reuse complex queries, hide complexity, stay consistent.
  • Transactions: START, COMMIT, ROLLBACK. Group statements so they all succeed or all undo.
  • SAVEPOINT / RELEASE SAVEPOINT: partial rollbacks inside one transaction.
  • Isolation and deadlocks: how concurrent transactions can interfere, and the famous mutual-wait pattern.
  • Indexes: data structures that speed up lookups on a column. Add them for slow filtered queries. Costs: disk space and slower writes.
  • Composite indexes: useful when queries filter on multiple columns together.
  • Data analysis: the same SQL primitives you've spent the course learning, wrapped in views where useful.
